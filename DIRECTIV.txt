06. CANONICALIZATION AND HASHING
Reuse existing hashing/canonical JSON utilities if verified sufficient. Do not replace existing provenance scheme or silently alter existing hash formats.

07. IMMUTABLE CONTEXT SNAPSHOT LIFECYCLE
State model: PREPARED -> SEALED -> CONSUMED (or REJECTED); exact mapping must respect existing workflow/job states. PREPARED may only reference authorized, current, pinned source versions. SEAL verifies source hashes, quote-lock/citation integrity where relevant, policy pins, and content digest in one consistent transactional view. SEALED content is immutable; changes create a new snapshot with a new digest and linkage to predecessor, never overwrite historical bytes. CONSUMED records which agent/job consumed which sealed snapshot. REJECTED records a safe reason code. If current schema already provides these semantics, reuse it and do not create tables. Otherwise add the minimum additive, tenant-scoped schema required. Snapshot lifecycle is not a new release state and cannot bypass review.

08. DATABASE AND TRANSACTION SAFETY
PostgreSQL remains authoritative. Reuse withTransaction and transaction-local tenant context. Verify every new tenant-scoped table has RLS with deny-by-default behavior, correct FORCE RLS or equivalent verified role discipline, tenant-filtered foreign-key/ownership checks, least-privilege grants, and non-bypass service roles. Verify pooled connections cannot leak tenant context after success, rollback, exception, or cancellation. Enforce idempotent creation by a unique tenant/job/context digest or equivalent tested key. Make snapshot sealing and consumption atomic with existing job transitions as required; ensure concurrent attempts cannot create conflicting seals. Use explicit uniqueness constraints and transactional conflict handling, not check-then-insert alone. Prefer existing transaction isolation; justify any stronger level through measured need. Do not introduce SQLite. Read-only replay must not write audit rows or mutate source state; any audit of replay must be a separate, explicitly authorized operation.

09. AUTHORIZATION AND CONTEXT MINIMIZATION
Bind authorization to the actual request/session and existing agent capability policy; enforce server-side on every materialized context read and consumption. Validate tenant + project + source ownership, source-version pinning, job/run ownership, task type, and agent capability together. Reject ambiguous/missing references. Return only task-relevant fragments; never broaden to unrelated source versions or tenants. Preserve negative-evidence and quote-lock semantics. Treat source documents as untrusted data: text cannot override policies, instructions, release state, or agent permissions. Cache entries must be bound to the full security-relevant context identity and invalidated on relevant policy/source changes. A cache-key difference alone is NOT proof of tenant isolation.

10. RECORD/REPLAY AND DETERMINISM
Provide a replay verifier for SEALED snapshots that reconstructs the exact authorized context and checks recorded hashes and pins without side effects. Separate three modes explicitly: (A) deterministic local transforms and fake provider, reproducible byte-for-byte under pinned versions; (B) recorded provider outputs, replayed from previously captured authorized outputs with provenance and integrity checks; (C) live LLM calls, which are NOT claimed deterministic. This phase does not authorize making live LLM calls or collecting new external data. Never fabricate a provider record. Replay must reject missing/changed source bytes, policy changes without a matching historical pin, missing provider records, tenant mismatch, and schema incompatibility. Historical policy may be used only to verify historical output, not to authorize a new live action. Replay cannot trigger release, export, email, upload, network calls, cache writes, or state transitions.

Use bounded memory, source-fragment counts, timeouts, and backpressure already consistent with project conventions. Benchmark p50/p95/p99 latency and errors on documented fixture sizes and concurrency levels; record baseline vs changed performance. Define and test no stale-policy authorization, no cross-tenant exposure, no double-seal, no partial snapshot visibility, no mutation of sealed data. Do not assert universal zero contamination, zero lock waits, or infinite scalability.
